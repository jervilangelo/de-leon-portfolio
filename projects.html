Nov 2026Web app · Open source

Turns Microsoft Project schedules into presentation-ready Gantt charts, with critical path analysis and delay simulation that shows what a slipped task does to Go-Live.

  • React
  • TypeScript
  • SVG Gantt
  • Node.js
  • MPXJ
  • Playwright
View project →

Microsoft Project is good for planning, but hard to explain in a meeting. Schedrift answers the question stakeholders actually ask: if this task slips, what happens to Go-Live? It imports .mpp, .mpx and Microsoft Project XML files and shows the whole plan in one presentation-ready view, without changing the original file.

Select one or more tasks, change their start or duration in working days, and the timeline and Go-Live variance update, along with the dependency chain driving the change. Dependencies are imported as defined (FS, SS, FF and SF, with lags), and a delay only reaches a successor when it uses up the gap already between them. Scenarios stay separate from the approved schedule. The showcase video above walks through it with a synthetic ERP rollout.

  • Executive and Detailed Gantt views, critical path focus and total float, on a custom SVG renderer with row virtualization.
  • Present mode for fullscreen meetings, baseline comparison, and Excel or CSV updates that keep the imported dependencies.
  • Local-first: a Node server bound to 127.0.0.1, no cloud, no login and no telemetry. .mpp files are parsed by Java and MPXJ from temporary copies and never modified.
  • The import report flags cycles, missing predecessors, invalid dates and unsupported features.
  • Vitest unit and integration tests and Playwright browser tests, all on synthetic schedules.

Nov 2026Cloud · Terraform

Disaster recovery through infrastructure as code: Terraform rebuilds a small business's system in AWS after a typhoon, from verified backups, in under six minutes.

  • Terraform
  • S3
  • EC2
  • VPC
  • IAM
  • Systems Manager
  • GitHub Actions
View project →

A disaster recovery proof of concept for Philippine small businesses. It protects a sample management system for a fictional farmers' cooperative in Naga City: members, inventory and a ledger in FastAPI and PostgreSQL 16 on Docker Compose. When a typhoon takes the office server offline, Terraform builds a temporary recovery site in AWS Singapore, restores a verified backup, and checks that the application works again.

Every hour the database is backed up with a snapshot-consistent pg_dump, restored into a throwaway test database and recounted before it counts as a backup. Verified copies go to an encrypted, versioned S3 bucket. In a recovery, a local job runner checks the backup and the Terraform plan, the operator approves, and the recovery host restores the data, checks its checksum, health and record counts, and reports the measured RTO and RPO before teardown.

  • Final real AWS drill: recovered in 5 min 29 s with 26 s of data loss, 10 of 10 checks passed. Targets were 30 minutes and 1 hour.
  • Standby costs cents a month: no servers run until a recovery is approved. Recorded compute spend for the whole project was about USD 0.01.
  • No SSH keys, no IAM users and no long-lived access keys: SSO for the operator, Session Manager for the host.
  • React and Vite dashboard live on GitHub Pages, with a simulated recovery walkthrough and the published drill results.

Infrastructure as code

The whole recovery site is Terraform

Nothing in AWS was clicked together. Five modules describe the recovery site, and one variable decides how much of it exists.

recovery_enabled = false

Standby. Backup bucket, IAM roles, log group and a budget alert. No servers; S3 storage is the only real cost.

recovery_enabled = true

Recovery. Adds the VPC, subnet, internet gateway, S3 endpoint, security group, EC2 host and a status alarm. Setting it back to false removes them and leaves the backups untouched.

  1. networkingVPC, one public subnet, internet gateway, free S3 gateway endpoint, and a security group with no inbound rules
  2. computet3.small on Amazon Linux 2023, IMDSv2 only, encrypted gp3, terminates on shutdown, bootstrapped from a template
  3. storagePrivate, encrypted, versioned backup bucket with lifecycle rules and a TLS-only policy
  4. identityHost role with Session Manager and read-only backups; an upload-only backup-writer role that cannot read or delete
  5. monitoringLog group with 7-day retention, host status alarm, AWS Budgets alerts at 50% and 100%
  • Remote state in S3Versioned, encrypted bucket with native S3 lockfile locking and prevent_destroy
  • Checked in CIfmt, validate, terraform test on a mocked provider, TFLint and Trivy in GitHub Actions
  • Plan guardThe job runner fails closed on an unexpected plan, and the operator types an approval before apply

terraform plan → plan guard → approval → apply → restore → verify → teardown

Nov 2026Web app · Open source

Free personal finance calculators built on official Philippine data: take-home pay, 13th month pay, MP2 and digital bank savings against inflation.

  • React
  • TypeScript
  • GitHub Actions
  • Playwright
View project →

"Worth it ba sa Pilipinas?" PinansyalPH is a free, open-source set of personal finance calculators built on official Philippine data. It works out take-home pay and 13th month pay, projects Pag-IBIG MP2 and digital bank savings after tax, and measures them against PSA inflation. It shows the arithmetic instead of telling people what to do with their money: no sign-up, no ads, no tracking, and inputs stay in the browser.

Every figure carries its source, reference period and retrieval date. A daily GitHub Actions workflow pulls PSA inflation and DOE fuel prices, validates them against shared zod schemas, keeps the previous file if a source fails, and commits only real changes. Bank rates and the MP2 dividend are checked by hand and never auto-published. The copy is in Taglish, and the showcase video above walks through the tools.

  • Seven tools: Sweldo, 13th Month Pay, MP2, Digital banks, Compare, Inflation and Gas.
  • Payroll follows SSS, PhilHealth, Pag-IBIG and BIR rules, versioned in one data file; 13th month pay follows PD 851 and checks the ₱90,000 tax exemption.
  • Money maths in decimal.js, rounded to centavos only where an institution would.
  • Savings shown in today's pesos; MP2 and bank products sit side by side, and nothing is ranked by headline rate.
  • 111 unit tests and 52 browser tests run before every deploy, across widths from 360px to 1920px.

An event-driven API for HRIS support tickets: API Gateway, Lambda and DynamoDB, with a stream that emails Critical tickets through SNS.

  • API Gateway
  • Lambda
  • DynamoDB
  • SNS

View project →

A serverless API for logging and tracking HRIS support tickets, modelled on the requests I handle at work, with made-up data. API Gateway takes the request, a Lambda function handles it and DynamoDB stores it. A DynamoDB stream feeds a second Lambda that emails me through SNS whenever a Critical ticket is created.

  • Six routes: CRUD, status and module filters, and a summary by status and module.
  • A status-index GSI turns status filters into queries instead of scans; SLA due dates are set by priority.
  • One narrow IAM role per function, no resource wildcards; API throttled to 5 requests a second.
  • JSON logs, one-week retention and a CloudWatch error alarm that emails through SNS.

API endpoints

Ticketing API routes

POST/ticketsCreate a ticket201

PUT/tickets/{id}Update status, assignee, priority or resolution notes200

Bad input returns 400 with a list of what is wrong, an unknown ticket returns 404, and anything unexpected returns a generic 500 while the details go to the logs. Updates and deletes use a condition check, so changing a ticket that does not exist returns 404 instead of quietly creating it.

Data model

  • One on-demand table, HrisTickets, keyed on ticketId (for example HRIS-70B503C7).
  • Fields for module, request type, priority, status, assignee and notes, with UTC timestamps; resolvedAt is set only on resolution.
  • A status-index GSI (status, then createdAt) makes status filters a query that returns the newest first, instead of a full scan.
  • SLA due dates by priority: Critical 4 hours, High 8, Medium 24, Low 72.

Security and permissions

  • hris-ticket-handler may only Put, Get, Update, Delete and Scan items on the table, and Query its index.
  • hris-critical-alert may only read the table's stream and publish to the hris-critical-alerts topic.
  • Neither policy uses a wildcard on its main resource.
  • The stage is throttled to 5 requests a second (burst 10) so a runaway script cannot run up a bill.
  • No authentication, acceptable for a short-lived test with fake data; a Cognito JWT authorizer would come first in a real deployment.

Monitoring and alerts

  • One JSON log line per request with the route and Lambda request ID; error details logged on failure.
  • One-week log retention on both functions.
  • A CloudWatch alarm on the handler's Errors metric emails me through SNS on one or more errors in five minutes; missing data counts as healthy.
  • The stream trigger uses batch size 10 from the latest record, so existing tickets never cause alerts.

What went wrong

  • Wrong region. I started building in the wrong region and had to remove everything and begin again in Singapore. Almost everything in AWS is regional, so I now check the region selector before every step.
  • Empty ticket ID. Two commands pasted onto one line left the ticket ID variable empty, so GET and PUT returned a plain 500: DynamoDB rejects an empty key, and the response did not say so. The structured logs showed the cause.

Limitations and next steps

  • Add authentication, with a Cognito JWT authorizer or API keys.
  • Paginate listing; without a status filter it is a Scan capped at 50 items.
  • Handle MODIFY stream events, so raising a ticket to Critical also alerts.
  • Convert timestamps from UTC to local time in the emails.
  • Rebuild it as an AWS SAM template so it deploys with one command.
  • Add a small frontend for demos.

Cost: Lambda, API Gateway and DynamoDB on pay-per-use pricing with tiny test traffic, so the cost was negligible.

A hands-on practice build for AWS networking and security: a static page served by Nginx on Amazon Linux 2023 inside a custom VPC (10.0.0.0/16) in Singapore. HTTP is open, SSH is limited to my IP, and Session Manager access comes from an IAM role on the instance. An EBS snapshot is the backup.

Why I built it

While studying for the AWS Certified Cloud Practitioner (CLF-C02) exam, I wanted to practise the services I was reading about instead of only memorising them, so I built a small but secure web server in a network I designed myself.

  • Apply EC2, VPC, security groups, IAM and EBS in one working project.
  • Follow security basics: no daily work as root, restricted access and cost controls.
  • Document the work so others can follow it.

Configuration

Architecture configuration
RegionAsia Pacific (Singapore), ap-southeast-1
VPCCustom VPC, 10.0.0.0/16, one Availability Zone
SubnetOne public subnet with auto-assign public IPv4
RoutingInternet gateway attached; route table sends 0.0.0.0/0 to it
ComputeEC2 on Amazon Linux 2023, Nginx installed by a user data script
StorageEBS volume with a snapshot as a backup
AccessSecurity group, plus an IAM role for Session Manager

How I built it

  1. Account setupPicked one region, enabled MFA on the root account, set a monthly budget with an 80% email alert, turned on Free Tier alerts, and created an IAM user with MFA in an admin group for daily work.
  2. NetworkCreated the VPC with one public subnet and no NAT gateway or VPC endpoints. Verified the internet gateway, created a public route table with a default route to it, and associated it with the subnet.
  3. ServerLaunched the instance, confirmed its status checks, and checked Nginx in the browser. Connected over SSH with a key pair, uploaded the site with scp, moved it into the Nginx web folder, and set file permissions to 644.
  4. BackupCreated an EBS snapshot of the instance volume and confirmed it reached the Completed state.

Security measures

  • Root account protected with MFA and not used for daily work.
  • Security group allows HTTP (80) from anywhere and SSH (22) only from my IP address.
  • An IAM role on the instance lets Session Manager act as a keyless backup way in.
  • No NAT gateway and a $5 budget alert as cost guardrails.
  • The private key stays off GitHub and is never shared.

Problems I solved

  • SSH "Permission denied (publickey)". The key file was not found because I ran the command from the wrong folder. The full path to the key, quoted because of spaces in the folder name, fixed it.
  • Key file permissions on Windows. The private key must be readable only by my user, so I removed inherited permissions and granted my account read access with icacls.
  • sudo error in PowerShell. I had run server commands on my own PC. Commands like sudo mv run on the server; scp runs on my computer.

Concepts it reinforced

  • Shared responsibility. AWS secures the infrastructure; I manage the OS, patches and security group rules.
  • Least privilege. Open only the ports and permissions that are needed.
  • Regions and AZs. Resources belong to a region, so staying in one avoids confusion.
  • Cost awareness. Public IPv4 addresses, NAT gateways and snapshots can all create charges.

Next steps

  • Add HTTPS with a domain name and certificate.
  • Automate the deployment with a script or infrastructure as code.
  • Add monitoring with CloudWatch.
  • Rebuild the setup with CloudFormation or Terraform.
  • Clean up: stop the instance when not in use, and delete the instance, snapshot and VPC when finished.
